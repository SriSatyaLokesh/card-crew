# Supabase-native schema

Implements [docs/DATABASE_DESIGN.md](../docs/DATABASE_DESIGN.md) and the RPC catalog from
[issue #3](https://github.com/SriSatyaLokesh/card-crew/issues/3), with the RLS hardening from
that issue's review already applied (not left as a follow-up).

This is **Phase A** of the agreed cutover (build in parallel, Express untouched — see the
issue's cutover phases). It does not yet touch the frontend, `wrangler.jsonc`, or CI deploy
config; those are Phase C/D/E, separate PRs.

## Layout

- `migrations/20260923000001_schema.sql` — extensions, enums, tables, indexes, triggers.
- `migrations/20260923000002_rls.sql` — RLS enablement + policies, `profiles_public` view.
- `migrations/20260923000003_functions.sql` — the RPC catalog + `current_user_id()` indirection.
- `seed.sql` — card catalog (issuers, networks, catalog items/cards, use cases), generated by
  [`scripts/generate-catalog-seed.js`](../scripts/generate-catalog-seed.js) from
  [`backend/src/catalog/card-catalog.seed.ts`](../backend/src/catalog/card-catalog.seed.ts) —
  edit the TS source and regenerate, don't hand-edit `seed.sql`.

## Running locally

Requires the [Supabase CLI](https://supabase.com/docs/guides/cli) and Docker.

```bash
supabase start        # local Postgres + PostgREST + GoTrue; auto-applies migrations + seed
supabase db reset      # re-apply from scratch after a migration change
```

**Not run in this session** — no Supabase CLI or Docker daemon was available in the
environment that authored this schema. Every statement was reviewed by reading, not by
executing. **Run `supabase start` locally before merging** and report back anything that
fails; treat this PR as unverified-by-execution until that happens.

## Privilege model

Every function is either `SECURITY INVOKER` (relies entirely on RLS — the default) or
`SECURITY DEFINER` (crosses into another user's data, individually justified). The full
audit list is the comment block at the end of `20260923000003_functions.sql`. If you add a
new function that touches another user's row, add it to that list and explain why `INVOKER`
wasn't enough — see the guardrail workflow below, which is meant to catch it if you don't.

## CI guardrails

[`.github/workflows/supabase-guardrails.yml`](../.github/workflows/supabase-guardrails.yml)
runs three SQL checks (`guardrails/*.sql`) against a fresh local Supabase instance on every
push that touches `supabase/**`:

1. Every `SECURITY DEFINER` function has `search_path=` pinned.
2. Every table in `public` has row level security enabled.
3. The `SECURITY DEFINER` functions in the database match the audited list above.

A fourth guardrail — grepping the built `frontend/dist` for the service-role key — belongs
here once the frontend adapter lands (Phase C); not added yet since there's no build output
to check.

These are meant to make the mistakes found in the original design review structurally
impossible to reintroduce, not just fixed once.
